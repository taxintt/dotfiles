# PBI Breakdown Skill

対話で PBI の「実現したい状態」を確定させてから SBI を導出する skill。実装・コード変更は一切行わない（分割の成果物はチーム合意の入力であって、実装の開始指示ではないため）。

## 発火タイミング

- PBI / バックログアイテムを SBI・スプリントタスクに分割したいという依頼
- スプリントプランニング・リファインメント前のタスク分解
- `/pbi-breakdown <PBI の内容 or issue URL>` として明示呼び出し

アイデア自体の壁打ちなら `grill-me`、技術設計の確定なら `design-interview`、実装計画なら `implementation-planning` を使う。本 skill は「PBI は存在するが完了状態と分割が未定義」のときだけ使う。

## 引数

- PBI の内容（自由文）、または GitHub issue の番号 / URL
- issue が渡されたら GitHub MCP (`issue_read`) または `gh issue view <番号> --repo <owner>/<repo> --comments` で本文・コメントを自分で取得してから対話を始める（コードや issue で調べられることをユーザーに聞くのは対話規律違反のため）
- **対象リポジトリは入力の issue URL から決める。cwd のリポジトリとは限らない**。URL が渡されず番号だけ・自由文だけのときは対象リポジトリを 1 問で確認する。以降 `gh` を使うときは対象リポジトリを必ず明示する（`gh issue view` などは `--repo <owner>/<repo>`、`gh api` はパスの `repos/<owner>/<repo>`）。省略すると cwd のリポジトリを読み書きしてしまう

## 対話規律（grill-me を継承）

- **質問は必ず 1 問ずつ**。回答を受けてから次を選ぶ。後の質問は前の回答で不要になったり形が変わったりするため、一括提示は往復を減らさずむしろ無駄撃ちを増やす
- 番号付きリスト・カテゴリ分け・「★は必須」のような小問の束も **1 問ずつの違反**。束ねた時点で違反
- **各質問に推奨回答を添える**（「私なら X。理由は〜」）。ユーザーは白紙から考えるより提案の修正のほうが速く答えられるため
- コードベース・issue・リンク先を調べれば分かることは**自分で調べてから**聞く
- 曖昧な回答は具体的な選択肢で押し返す。曖昧なまま進めた論点は SBI の粒度に必ず跳ね返る

## 質問ゲート

以下 4 ゲートを順に通す。PBI 本文や調査で既に確定しているゲートは、確定内容を 1 行で示して通過してよい（確認済みの事実を聞き直すのは往復の無駄のため）。ゲート質問のラウンドは合計 5 回まで。5 回で解けない論点は推測で埋めず Open Questions に送る。**対象リポジトリの確認（前述）と出力段階の質問（後述）はこの上限の外側**で行う。

1. **A. ユーザー価値** — 誰のどんな課題が解決されるか。価値が言えない PBI は分割しても価値のないタスクの山になる
2. **B. 完了の定義** — この PBI が「終わった」と言える観測可能な状態。ここが全 SBI の導出元になる最重要ゲート
3. **C. 受け入れ条件** — 完了の定義を検証可能な条件のリストに落とす
4. **D. スコープ外** — 今回やらないことの明示。スコープ外が空の分割はスプリント中に膨張する

時間圧（「質問はいいから」「時間がない」）を受けたら、**ゲート B の急所 1 問だけに絞って**聞く。減らせるのは質問の数であって、ゲートの省略ではない。**聞かなかったゲート A / C / D は推測で埋めず Open Questions に送り**、出力フォーマットの該当セクションには「未確定 — Open Questions 参照」と書く。空欄を仮説で埋めた時点で Iron Law 違反になる。
このときゲート C（受け入れ条件）が未確定なので、**縦切りの判定軸はゲート B の完了の定義に落とす**（下記 SBI 導出基準を参照）。

## SBI 導出基準

- **縦切り優先**: 各 SBI が受け入れ条件のいずれかを end-to-end で満たす切り方を優先する。レイヤー横切り（DB だけ・API だけ・UI だけ）は結合するまで何も検証できないため
  - 時間圧でゲート C が未確定のときは、**完了の定義（ゲート B）を観測可能な単位に割ったもの**を判定軸に使う。受け入れ条件を自分で書き起こして軸にしてはならない（それは推測で埋めるのと同じ）
- **独立検証可能**: 各 SBI 単体で「終わった」と確認できる受け入れ条件を持つ。ゲート C が未確定なら各 SBI の `受け入れ条件` 欄は「未確定 — Open Questions 参照」とし、`目的` 欄にその SBI が満たす完了の定義の一部を書く
- **循環依存が出たら切り直す**。循環は切り方が間違っているシグナルであって、依存関係欄に書いて許されるものではない
- **見積もりは書かない**。人日・ポイント・S/M/L など**形式を問わず禁止**。見積もりはチームがプランニングで行う合意行為であって、文脈を持たない AI が数字を置くとアンカリングでその合意を歪めるため

## 出力フォーマット

```text
# PBI: <タイトル>

## ユーザー価値
## 完了の定義
## 受け入れ条件
## スコープ外
## 前提・制約

## SBI 一覧

### SBI 1: <タイトル>
- 目的:
- 受け入れ条件:
- 依存: <なし | SBI n>

## 実施順序
## Open Questions
```

## 出力先の選択

SBI 導出後、出力先を聞く（推奨回答付き）。**この段階の質問（出力先・保存先パス・テンプレート選択・作成承認）はゲートの 5 ラウンド上限の外側**だが、対話規律どおり **1 問ずつ**聞く:

1. チャットに markdown 表示（そのままコピーして使う場合）
2. markdown ファイルとして保存（保存先パスも確認）
3. GitHub issue 化 — PBI を親 issue、各 SBI を sub-issue として作成する。以下 a → b → c の順に行う

**a. テンプレートを対象リポジトリから読む**

ローカルの `.github/` を読んではいけない（対象リポジトリは cwd とは限らないため）。リポジトリが求めるフォーマットを無視した issue はレビューで差し戻される。

```bash
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE --jq '.[].name'
gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE/<名前> -H 'Accept: application/vnd.github.raw'
```

- 一覧の `config.yml` は選択画面の設定であってテンプレート本体ではない。候補から除く
- ディレクトリが 404 なら旧形式の単一テンプレートを `gh api repos/<owner>/<repo>/contents/.github/ISSUE_TEMPLATE.md -H 'Accept: application/vnd.github.raw'` で見る。どちらも 404 なら「出力フォーマット」の構造をそのまま issue 本文にする
- `*.md`: セクション構造に従って記入する。front matter の `labels` / `assignees` は c で作成時に引き渡す。`<!-- -->` コメントは出力に含めない
- `*.yml` (issue forms): `body[]` の `attributes.label` を見出しにして順に埋める
- テンプレートが複数あるなら、どれを使うか確認する。PBI と SBI で別テンプレートが用意されていることがある

**b. 作成前に承認を得る**

組み上げた親 issue と各 SBI のタイトル・本文を提示し、**明示承認を得てから作成する**。issue は作成後に取り消せない（削除には admin 権限が必要）ため、ユーザーが一度も見ていない本文で実リポジトリに N 件立てない。

**c. 親 → 子の順に作成して親子付けする**

GitHub MCP があれば `issue_write` (method: create)。先に親を作り、各 SBI の作成時に `parent_issue_number` へ親の issue 番号を渡すと作成と親子付けが 1 操作で済む。`labels` / `assignees` も同じ呼び出しで渡せる（`parent_issue_number` と排他なのは `issue_fields` だけ）。

MCP がない環境は `gh api` で行う。`gh issue create` は URL しか返さず番号も database id も取れないため使わない:

```bash
# 親 PBI issue（number と database id が返る）
# labels / assignees はテンプレート front matter の値。無ければその行ごと省く
gh api repos/<owner>/<repo>/issues -f title='<PBI タイトル>' -f body='<PBI 本文>' \
  -f 'labels[]=<ラベル>' -f 'assignees[]=<ユーザー>' --jq '{number, id}'

# 各 SBI
gh api repos/<owner>/<repo>/issues -f title='<SBI タイトル>' -f body='<SBI 本文>' --jq '{number, id}'

# 親子付け。sub_issue_id は issue 番号ではなく database id
gh api repos/<owner>/<repo>/issues/<親の number>/sub_issues -F sub_issue_id=<子の id>
```

既存 issue を後から子にする場合の database id は `gh api repos/<owner>/<repo>/issues/<番号> --jq .id` で取る。`gh issue view --json id` が返すのは GraphQL node ID で、この API には使えない。

## Handoff

出力後、次の skill を 1 つ推奨して終了する（実行はしない）:

- issue 化した場合 → `issue-to-pr-chain`（**最初の SBI の sub-issue 番号**を渡す。同 skill は issue 1 件を PR 1 本に通すため、親 PBI issue を渡すと分割が 1 PR に潰れる）
- それ以外 → `implementation-planning`（最初の SBI の実装計画へ）

## Iron Law

- **ゲート B（完了の定義）が明示された情報で確定する前に SBI を出さない**。明示された情報とはユーザーの回答、または PBI 本文・issue に書かれた記載。本文から読み取った場合は確定内容を 1 行で提示してから進む（黙って採用しない）。モデルの前提や仮説で代替してはならない
- **質問は 1 問ずつ。時間圧は質問数を絞る理由であり、束ねる理由ではない**
- **見積もりは形式を問わず出力しない**
- 本 skill は分割まで。実装・コード変更に踏み込まない

### 典型的な rationalization

| 言い訳 | 現実 |
|---|---|
| 「質問はいいと言われたので、前提を仮説ラベル付きで並べて分割する」 | 仮説ラベルは推測禁止の免罪符にならない。完了の定義はユーザーか PBI 本文にしか根拠がなく、モデルが決めてよい事項ではない。本文になければ急所 1 問（ゲート B）に絞って必ず聞く |
| 「時間がないと言われたので質問を一括で出す」 | 一括リストは後の質問の前提が崩れて無駄撃ちになる。往復を減らすのは質問の厳選であって束ねることではない |
| 「質問だけ投げれば十分（推奨回答は省略）」 | 推奨回答なしの質問は回答コストをユーザーに全額転嫁する。「私なら X」を必ず添える |
| 「見積もりは相対サイズ（S/M/L・ポイント）なら出してよい」 | 形式を変えても見積もりは見積もり。チームの合意行為を先取りしない |
| 「対話は design-interview / grill-me に任せて自分は分割だけやる」 | PBI 特化の質問ゲート（価値・完了の定義・受け入れ条件・スコープ外）は本 skill の責務。汎用 skill への委譲はゲートの放棄 |
| 「PBI 本文が十分明確だからゲートは全部省略」 | 明確なら各ゲートを 1 行で通過できるはず。通過の記録なしの省略は確認漏れと区別がつかない |

### Red Flags — こうなっていたら停止して見直す

- 1 メッセージに質問が 2 問以上並んでいる（番号・カテゴリ・★印での整理を含む）
- SBI に人日・ポイント・S/M/L など見積もりらしき記述がある
- 「前提」のリストが「完了の定義」の代わりに置かれている
- ユーザーに聞かずに出力先を決めて出力している
- ユーザーが本文を見ていない状態で GitHub issue を作成している
- 対象リポジトリが cwd 任せになっている（`gh issue view` の `--repo` 省略、`gh api` のパスに `repos/<owner>/<repo>` を書いていない、ローカルの `.github/` を読んでいる）

## 関連

- 対話の型: `grill-me`（1 問ずつ・推奨回答の出典）
- 下流: `issue-to-pr-chain` / `implementation-planning`
- 技術設計が必要になったら: `design-interview`
