# Design Interview Skill

ユーザーの設計対象について **質問フェーズを駆動する**。不明点がなくなったら設計書作成に進む。**設計書は質問が完了するまで書かない**。

## 発火タイミング

- 新システム / 機能の設計に着手したい
- 設計に入る前提の要件が曖昧で、設計が進まない（要件そのものの妥当性を疑う段階なら `grill-me`）
- 設計方式（どのアーキテクチャで行くか）を決めて設計書に落としたい
- ユーザーが明示的に `/design-interview` と呼んだとき

## 引数

`[システム / 機能の概要]` — あれば初期コンテキストとして取り込む。未指定なら会話文脈から推定。

## 初期ステップ

1. **提供情報の整理**
   - ユーザー引数、会話文脈、既存ドキュメント、関連コードを確認
   - Git ブランチ名を `git rev-parse --abbrev-ref HEAD` で取得し、チケット番号らしき数字列を抽出（見つからなければ「なし」と記録）
   - ユーザーに再入力を求めない

2. **規模の見立て**
   - 規模を推定:
     - **小**: 個人 / 内部 CLI / プロトタイプ
     - **中**: チーム / 部門 SaaS / Web アプリ
     - **大**: 社内全体 / 外部公開
   - 規模に応じて質問プロファイルを切り替える

## 初回応答の構造（40 行以内）

```text
以下の情報を確認しました：
- 対象: <summary>
- ブランチ / チケット: <branch name / ticket or なし>
- 既存ドキュメント: <あれば要点 / なければ「なし」>

現時点で分かっていること:
- <箇条書き>

分かっていないこと:
- <箇条書き>

以下 <N=3-5> 点を教えてください。

1. <質問>
2. <質問>
...
```

## 質問プロファイル（規模別）

### 小規模
- 初回 3-4 問、最小要件に絞る:
  - 入力 / 出力の形式
  - 主要な処理内容
  - 実行環境 / 配布方法
- **パフォーマンス・ベンチマークは尋ねない**（ユーザー明示要件時のみ）
- 設計書構成要素は必要なもののみ

### 中規模
- 初回 4-5 問:
  - 目的 / 解決したい課題
  - 主要ユーザーと想定規模
  - 必須機能（MVP スコープ）
  - 制約（技術 / 期限 / 既存システム連携）
- パフォーマンス質問は後続ラウンドで 1-2 項目

### 大規模
- 初回 5 問、以降ラウンドを重ねる:
  - 目的 / ステークホルダー
  - ユーザー規模（同時接続 / ピーク / 将来見込み）
  - 機能要件 / 非機能要件
  - 制約（予算 / 期限 / 技術スタック）
  - セキュリティ / コンプライアンス
- パフォーマンス・ベンチマークは必ず確認（目標レスポンス / 計測方法）

## 質問ラウンドの上限

質問は **要件ヒアリング → 方式の決定** の 2 フェーズで、予算は別々に持つ。

**要件ヒアリング — 最大 5 ラウンド**

- 使い切ったら打ち切り、未解決は設計書の「Open Questions」に送る
- 打ち切っても**「方式の決定」へは進む**。要件が全部揃っていなくても、確定した範囲で方式は選べる（方式だけは Open Questions に送れない。未定のまま書いた設計書は、モデルが黙って選んだ方式の設計書になる）
- ユーザー疲弊の兆候があれば「**残りの要件は Open Questions に回して、方式だけ決めてドラフトに進みますか？**」と提案する。「設計書に進みますか」とだけ言うと、この後に方式決定の数ラウンドが続くことを隠すことになる

**方式の決定 — 案の数 + 1 ラウンド**（2-3 案なら 3-4。各案の確認 + 採用の決定）

- **曖昧な回答への押し返しは予算の外側**。「お任せ」「状況による」のような決定でない返答には、Iron Law どおり推奨案とその理由を示して選ばせる（予算は最小ラウンド数ちょうどなので、内側に置くと押し返す余地が無い）
- 押し返しは 1 案につき 1 回まで。それでも決まらなければ、**設計書を書かずに停止し**、比較した案・トレードオフ・決めきれなかった論点を報告する

## 方式の決定

要件ヒアリングを終えたら（予算切れで打ち切った場合も含む）、設計方式を **2-3 案**挙げ、**1 ラウンドにつき 1 案**を扱う（前の案への評価で次の案の見方が変わるため、全案を並べて「どれがいいですか」と聞いても答えは返ってこない）。各ラウンドでその案について以下を自分の見立てとして示し、**合っているかを 1 問で聞く**:

- 何を最適化する案か
- 捨てるもの（トレードオフ）
- この要件で効くか

全案を回したら、**最後の 1 ラウンドでどれを採るかを聞く**（推奨案とその理由を添える）。案ごとの確認だけで予算を使い切ると、採用の決定を聞かないまま停止分岐に落ちる。

**1 案しか出せないなら、それは比較ではなく前提**。なぜ他の案が落ちるのかを言えないまま採用しない。採用案と**不採用案・不採用理由**を設計書に記録する（後から「なぜこの構成か」を問われたときの答えがここにしかないため）。

要件が明らかに 1 方式に決まる規模（小規模の追加実装など）なら、その旨を 1 行示して通過してよい。

## 設計書に進む条件

**必須（揃うまで進まない）**

- 設計方式が決まり、不採用案の理由（または 1 方式に決まる理由）が言える

**目標（ラウンドを使い切っても未確定なら Open Questions に送って進む）**

- 目的 / 対象ユーザー / 必須機能が具体的
- 技術スタックと制約が確定
- データフロー / 主要コンポーネントの方向性が決まっている
- 規模に応じたパフォーマンス要件（小規模は不要、中・大は確認済み）

## 設計書の構成要素（規模に応じて取捨）

| 項目 | 小 | 中 | 大 |
|---|---|---|---|
| チケット番号 / 概要 | ○ | ○ | ○ |
| 要件定義（機能 / 非機能） | ○ | ○ | ○ |
| 採用方式と不採用案の理由 | ○（1 方式に決まる場合はその理由） | ○ | ○ |
| システム構成図 | 任意 | ○ | ○ |
| データモデル | 任意 | ○ | ○ |
| API 仕様 | 任意 | ○ | ○ |
| 画面遷移 / UI | 任意 | 任意 | ○ |
| セキュリティ設計 | 任意 | ○ | ○ |
| エラー処理方針 | ○ | ○ | ○ |
| パフォーマンス / ベンチマーク | 不要（明示要件時のみ） | 必要 | 必須 |
| 運用・保守 | 任意 | ○ | ○ |
| 拡張計画 | 任意 | 任意 | ○ |
| 参考資料 | ○ | ○ | ○ |

## Iron Law

- 「たぶん」「おそらく」という推測で進めない
- ユーザーが「適当でいい」と言っても、具体的な選択肢を示して決定を求める
- **質問フェーズ中に設計書を書き始めない**
