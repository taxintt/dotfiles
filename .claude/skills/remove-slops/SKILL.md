# Remove Slops Skill

AI 生成コードに混入しがちな "slop" を検出・除去する。AGENTS.md の「デバッグコード残置禁止」「最小限の実装」原則の実行スキル。

## 発火タイミング

- AI が生成したコードに冗長な部分を感じる
- ユーザーが「slop 除去」「不要コメント削除」「AI っぽいコードを直して」と依頼
- `/remove-slops` として明示呼び出し

## Slop の定義

除去対象:

### 1. 不要コメント
- 「何をするか」を繰り返すだけのコメント (`// This function calculates the sum`)
- 自明な処理の説明 (`// increment i by 1`)
- 関数名・変数名をそのまま言い換えたコメント

### 2. 過剰な defensive check
- 到達不可能なエラー処理 (型システムや上位の制約で不可能なケース)
- 呼び出し元が保証しているものを再検証するガード
- フレームワークがすでに処理しているエラーを再キャッチ

### 3. 冗長な型・キャスト
- 明示的に推論できる型アサーション
- 不要な型変換・キャスト

### 4. AI 特有の冗長パターン
- `// Handle the case where X` 系の文脈なしヘッダーコメント
- 意味のない `// TODO: add more logic here`
- 空の catch ブロックのコメント `// This should not happen`
- デバッグ用 print / log を残したまま

### 5. 過剰な抽象化の痕跡
- 一度しか使われない helper 関数 (インライン化すべきもの)
- 無意味なラッパー変数 (`result := calculate(); return result` → `return calculate()`)

## 除去しないもの

- WHY が非自明なコメント (隠れた制約・特定バグへの対処・驚くべき実装)
- ドメイン知識が必要なコメント
- 意図的なエラーハンドリング (起こりうるエラーを処理)
- 公開 API のドキュメントコメント

## 手順

### ステップ 1: 対象ファイルの特定

引数でファイルパスが指定された場合はそのファイル。未指定の場合:
- `git diff --name-only` で直近の変更ファイルを取得
- または「どのファイルを対象にするか」をユーザーに確認

### ステップ 2: Slop の検出と分類

対象ファイルを読み込み、各 slop を以下で分類:

- **SAFE**: 明確に不要、除去してもロジックに影響なし
- **CAUTION**: 除去すると可読性が下がる可能性あり、確認推奨
- **KEEP**: 実は意味がある、除去しない

### ステップ 3: 変更前の確認

SAFE 判定の slop 一覧を提示し、確認を求める。
CAUTION 判定は理由とともに個別に確認する。

### ステップ 4: 除去の実行

承認後、ファイルを編集。除去後:
- コンパイル / 型チェックが通ることを確認
- テストが通ることを確認 (該当する場合)

## Iron Law

- **承認なしの削除禁止**: 必ず確認してから変更する
- **機能変更禁止**: ロジックは一切変えない。slop の除去のみ
- **過剰除去禁止**: 「たぶん不要」は KEEP に分類
- **リファクタ禁止**: 「ついでに」型の改善はスコープ外

### 典型的な rationalization

| Rationalization | 対処 |
|---|---|
| 「コメントがないと読めない」 | そのコメントは WHY を語っているか確認。YESなら KEEP |
| 「このエラーは起きないから消せる」 | 本当に型・フレームワークで保証されているか確認 |
| 「ついでにリネームも」 | スコープ外。slop 除去だけに留める |
